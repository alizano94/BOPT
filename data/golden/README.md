# Golden fixtures

Reference data that a clone **cannot regenerate**, and which is therefore committed
despite looking like derived output. See the note at the bottom of `.gitignore`.

---

## `summit_snar_nsga2.csv`

10,000 SnAr evaluations produced by **real Summit**, used by
`tests/test_snar_vs_summit.py` to check the port against the reference
implementation.

| | |
|---|---|
| Source | [`experiments/snar_benchmark/data/pareto_front_snar.csv`](https://github.com/sustainable-processes/summit/blob/main/experiments/snar_benchmark/data/pareto_front_snar.csv) |
| Generated by | `experiments/snar_benchmark/pareto_front.py`, NSGA-II via `platypus`/`pymoo` |
| Columns kept | `tau, equiv_pldn, conc_dfnb, temperature, sty, e_factor` (metadata columns dropped) |
| Retrieved | 2026-08-11 |

### Why it is committed

Summit requires Python `<3.11`; BoTorch requires `>=3.11`. The two cannot share an
environment, so this project can never run Summit to regenerate these numbers. From
the surviving project's point of view the file is **source**, not output.

### Two caveats, both important

**1. It was generated by a pre-2020-06-20 Summit, whose E-factor differed.**

Versions before commit
[`e10d139e`](https://github.com/sustainable-processes/summit/commit/e10d139e1)
computed the waste sum as `for i in range(5)` — including the *product itself*.
The current formula excludes it (`if i != 2`). So:

```
E_old = (solvent + waste + product) / product = E_current + 1
```

exactly. Comparisons against this file must add 1 to the current implementation's
E-factor. This was diagnosed numerically (`ours − theirs ≈ −1.00` on every row)
before being confirmed in the git history.

Because `x → x + 1` is strictly monotone, **Pareto dominance is unaffected** and the
non-dominated set is identical under both definitions. The formula change does not
alter any conclusion about the front.

**2. The stored values are numerically imprecise.**

Summit runs `solve_ivp` at scipy's defaults (`rtol=1e-3`). Measured against a
converged solution (`rtol=1e-10`):

| | median error | p99 | max |
|---|---|---|---|
| This file | 2.0e-3 | 1.4e-1 | **7.0e-1** |
| Our port at the same loose tolerances | 1.1e-4 | 4.4e-4 | 6.2e-4 |

The reference data carries errors up to 70%, concentrated at high temperature and
high equivalents where the reaction is fastest. Our port at *identical* tolerance
settings is three orders of magnitude more accurate, presumably because of six years
of changes to scipy's adaptive step-size control.

**Consequence:** this file supports a *provenance and formula* check, not a precision
regression check. `tests/test_snar_vs_summit.py` therefore asserts distributional
agreement rather than pointwise equality, and its thresholds are set by this file's
own uncertainty. A precision fixture would need to be generated by running current
Summit under modern scipy in a disposable Python 3.10 environment.
